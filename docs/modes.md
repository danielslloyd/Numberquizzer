# Activity modes

Detail for the twenty-two bespoke activity modes. These are the **practice**
half of the app; the assessment half is documented in `docs/learn.md`.

Split out of CLAUDE.md, which had grown past the point where anyone would read
it end to end. CLAUDE.md now holds the invariants; this holds the per-mode prose.

## Interactive learning modes

These are screen-based games (not PDF generators), each driven from `TAB_ENTRY` in `app.js`:

- **Times Tables** (`times-grid-screen`, `tt*` functions) — 11×11 multiplication grid. Two modes via toggle: **Explore** (tap a cell to reveal/hide the product; shows a big `r × c = p` equation in `#tt-equation` below the grid) and **Quiz** (`ttAutoSelect` auto-picks an unfilled cell; answer in the `#tt-quiz-bar` input; correct fills green and auto-advances, wrong shakes). Active cell highlights its row/column factor headers. Per-fact mastery stored in localStorage as `ttFact_<r>x<c>` (correct-answer counter). Grid size set by `#tt-max` (5/10/12).
- **Fractions** (`fractions-screen`, `fr*` functions) — three sub-modes via toggle (`frSetMode`) and three difficulty tiers (`frSetLevel`, `FR_LEVELS`) in place of the old "up to <denominator>" select. A tier is a pool of denominators plus `gap` (the smallest value difference a non-equal Compare pair may have, so Easy never asks you to eyeball 6/11 against 7/12), `eqChance` (how often a Compare round is genuinely equal) and `simpMax` (the denominator ceiling for Simplify, deliberately above the compare pool so 18/24 can exist). **Every fraction in the tab is written strictly numerator-over-denominator** via `frFracHTML` / `.fr-frac` — there is no slashed `a/b` anywhere, including feedback lines. **Compare** (`frNewCompare`/`frComparePick`) puts the two shapes **side by side** with an operator slot between them; clicking a card claims it is the bigger one and reveals a big `>` or `<` where the slot is, and a **dashed circle** in that same slot is the "they're equal" answer, revealing a big `=`. The circle is present on every round — showing it only on equal rounds would announce the answer — and both children share one grid cell so the reveal lands exactly where the circle was without nudging the cards. Equal pairs come from `frEqualPair`, which groups the tier's fractions by lowest terms and draws two different writings of the same amount (1/2 against 2/4); unequal pairs come from `frUnequalPair`, which enumerates rather than reject-samples. `frCompareNode` records the round against `frac.compare.sameDen` / `.sameNum` / `.unlike` or `frac.equivalent.recognise` depending on what the two fractions share. **Build** and **Simplify** share one workbench (`#fr-work`): an example on the left, a live preview on the right, and a relation glyph (`#fr-rel`, `≠` grey / `=` green) between them that updates on every press. The preview is driven by four stepper buttons laid out as a pressable fraction (`− n +` over `− d +`); `frStep` clamps the numerator to the denominator and the denominator to `frState.maxDen`, and `frWireHold` adds press-and-hold auto-repeat because a top-tier Simplify round is a dozen presses. There is **no submit button** — `frCheckWork` runs on every press and the round ends the moment the preview is right. Build starts at **1/1** and hides the example's numbers (`?` over `?`), because reading the picture is the exercise; it wins on an exact `num`/`den` match, and an equivalent-but-differently-cut preview gets the nudge "Same amount — now match the pieces". Simplify shows the source's numbers and starts the builder holding a **copy of the source** rather than 1/1 — sweeping up from 1/1 passes through every unit fraction, so any source equal to a half would be solved by the first press; it wins on an equivalent value in lowest terms, with "Equal — but it can go simpler" standing until then. Sources come from `frSimplifiable`, a lowest-terms base scaled by k, so there is always something real to cancel. Every shape in the tab is a **pie** (`frRenderPie`) — the bar/pie toggle is gone. The fractions themselves are drawn at **twice** the old size, and the operator slot is aligned to the **fraction labels rather than the pies**: `.fr-shape-card` is a two-row grid whose second row is exactly `--fr-label-h` tall, and `.fr-op-slot` is given that same height plus a bottom inset of `--fr-card-pad + --fr-card-border`, so both centres land on the same line without anything being measured at runtime. Under 480px the pies give up width (`clamp(84px, 28vw, 170px)`) rather than the numerals shrinking, which keeps the full 2x on a phone; that media block must stay **after** the rules it overrides, since the selectors have equal specificity and source order decides. `frRenderBar` stays in `app.js` because `item-draw.js` renders Learn's fraction items with it; it is not dead code. A one-piece pie is special-cased to a plain `<circle>`, because an SVG arc whose start and end coincide draws nothing at all and the Build preview starts at 1/1.
- **Make Ten** (`make-ten-menu` → `tap-game`, `tg*` / `TAP_MODES` / `startTapGame`) — tap the number that completes the target. A **deck** is one card per complement `0..target` (`buildDeck`); the menu's **Reps** selector (`#mt-reps-btns`, default 1) makes that many copies which are **shuffled together** (`tgShuffle`) into one run — not sequential passes — so best-time (`bestKey`) is per target *and* reps. Round count is `state.tgRounds.length` (never a fixed 10). For target 10 the choices render as a **keypad** (`tgRenderRound` sets `.tg-keypad` + per-button grid position: 1–9 in a 3×3, 0 left of 1, 10 right of 9); other targets stay a flat wrap. Count-up stopwatch as before. Optional `#mt-tenframe` adds a ten-frame visual (`tgRenderVisual`) showing the known addend as filled dots.
- **Place-value visualizer** (`place-value-screen` / `viz-place-mode`, `pv*` functions) — its own tab, **Place Value**. Enter a number (`#pv-input`); `pvRender` draws base-ten blocks as SVG to scale — ones (unit cubes), tens (rods), hundreds (flats), thousands (10×100 columns of stacked hundred-flats) — each place a distinct color with a large bold digit label beneath. Above the blocks, `pvWords`/`pvRenderWords` write the number in **colour-coded words** ("one thousand, two hundred and thirty-four", British *and*), each place matching its block colour (`PV_PLACES`), connectors grey. A play button (`#pv-play`) reads it aloud via `pvSpeak` preferring an `en-GB` voice. viewBox auto-fits (`xMidYMax meet`); updates on every keystroke. The 3D Three.js multiply visualizer is the separate **Multiply** tab (`visualizer-screen` / `viz-multiply-mode`) — the two were one tab with a sub-mode toggle until 2026-07-31. An **animated count-up** (`pv-animate`, `pvAnim*`) counts from zero to the number one unit cube at a time; each time a place reaches ten, those ten pieces close ranks, take the next place's colour, and slide across into it, and a speed slider (`#pv-speed`, 1-40 cubes/second) sets the pace. Design notes: the frame reserves **ten slots in every place the target uses** (`PV_SLOTS`, `pvAnimLayout`) rather than the target's own digits, because a place must be able to hold ten before it can spill and a frame that resized mid-count would move everything under the eye. Every merge is a **pure translation plus a colour fade** — ten cubes with their gaps closed *are* a 1x10 rod, ten rods *are* a 10x10 flat, ten flats *are* a 10x100 column (`pvClosedXY`) — so nothing resizes and the ten parked pieces are swapped for the single real piece only once they are stacked and in place, where the swap cannot be seen. Carries cascade (999 + 1 merges three times before the count moves on). Tweens complete on a **timeout as well as on rAF**, because requestAnimationFrame does not fire in a hidden tab and the driver only advances from a tween's callback. The running digit under each place updates with the blocks, and the words above count up too; when it finishes it settles onto the canonical static picture so a number looks the same however you arrived at it.
- **Money visualizer** (`money-screen`, `mn*` functions) — four sub-modes via toggle (`mnSetMode`): **Identify** (`mnNewIdentify`/`mnCheckIdentify`; a random amount is shown as pieces, user types it), **Build** (`mnNewBuild`; tap denomination buttons to reach a target, with live total, undo/clear, and a fewest-pieces check on success), **Change** (`mnRenderChange`; enter an amount and pick a breakdown chip — exact change, coins only, or novelties like "All 1¢") and **Shopping** (`mnShop*`; spend a budget on a catalogue without going over). Five currencies in `MN_CURRENCIES` (USD default, GBP, EUR, CAD, AUD), each a list of denominations valued in **minor units** (cents/pence); choice persists in localStorage as `mnCurrency`. Identify/Build share the range select (`#mn-range`: under $1 / under $1000), which also drives the denomination pool via `mnPool` (a $1 bill is no use under $1).
- **Polygons** (`polygons-screen`, `py*` functions, all in `polygons.js` + `polygons.css`) — lazily loaded plug-in, same self-contained pattern as `language-arts.js`. Two sub-modes via toggle (`pySetMode`). **Draw** builds a regular polygon of any side count from 3 to 20, driven by a `−`/`+` pair and a slider; four chips overlay **diagonals**, **lines of symmetry**, **interior angle arcs** and a **spin**, and a fact grid gives sides, corners, angle sum, each angle, the turn at each corner, lines of symmetry, rotational order and diagonal count. **Quiz** asks multiple choice over eight question types — name the shape, count the sides, regular or irregular, lines of symmetry, angle sum, each interior angle, the exterior turn, and diagonal count — across easy/medium/hard tiers (`PY_LEVELS`, which set both the side range and which types are in play — **anything answered in degrees is Hard only**, so Easy and Medium stay on counting and naming), with an optional **Include irregular** chip. Every answer comes with a worked explanation. Geometry rules worth keeping: vertices start at `90 + 180/n` **in SVG screen space** (y increases downward), which puts a flat edge along the bottom at every side count — at the more obvious `-90` a square renders as a diamond. `pyIrregularPts` jitters each vertex's radius and angle but **keeps the angles sorted**, which makes the polygon star-shaped and therefore guaranteed simple; a plain scatter of points is not. `pySymmetrySVG` collects both families of axis direction (through vertices, through edge midpoints) and dedupes modulo 180°, which lands on exactly n axes for odd and even n alike without a parity special case. Questions whose answer depends on the shape being regular (interior angle, exterior angle, symmetry) are never asked of an irregular one; angle **sum** may be, since holding for any polygon is the point. Distractors (`pyNumericChoices`) are the correct answers for neighbouring side counts plus the classic misconception for that type — the exterior-angle question offers the interior angle, the angle-sum question offers `n × 180` — so a wrong pick is a diagnosis rather than noise. `window.__PY` is a debug handle used by the smoke test.
- **Patterns** (`patterns-screen`, `np*` functions, all in `patterns.js` + `patterns.css`) — lazily loaded plug-in: number sequences, four-way multiple choice, three tiers. A sequence is shown as tiles with one tile blanked; answering reveals the blank **and the step between every pair of tiles** (`+7`, `×2`, `÷2`), which is the explanation rather than a decoration. Score and streak, and the two question kinds record against different proficiencies — continuing a sequence is `alg.pattern.extend`, naming its rule is `alg.rule.apply`. Structure: a **family** builds one kind of sequence and says its rule in words (`arith` counting on, `geom` multiplying and halving, `grow` a step that itself grows, `square`, `triangle`, `fib`, `alt` two operations taking turns, `weave` two sequences interleaved); a **kind** is what is asked — `next`, `missing` (a term from the middle, which cannot be answered by carrying on), or `rule`. Tiers pick from both: **easy is plain counting on only** (`2, 3, 4, 5, 10`, starting on a multiple, next-term only — counting by *one* is deliberately not in the pool), medium adds multiplying, growing steps, alternating steps and triangular numbers plus the missing and rule kinds, hard adds squares, Fibonacci, weaving, halving and larger or negative steps. Correctness rules worth keeping: **the generator is not trusted** — every family carries a `holds` predicate that re-derives the pattern from the finished terms and `npMake` discards a sequence its own family cannot see the pattern in. **Exactly one option may fit**: for next/missing no distractor may sit in the blank and leave `holds` true, and for rule questions no distractor may be a true description of the terms; two defensible answers is the failure mode this mode has, and the smoke test checks both directly against an independent rule parser. Distractors are mistakes people actually make — one step too far or short, the step applied to the wrong term, addition mistaken for multiplication — because a random number is a free pass. All the `add N`/`subtract N` strings come from one `arithRule` helper, since built by hand they read "add -9 each time" as soon as a step goes negative. Step labels come from `npStepLabels`, computed from the terms on screen rather than from what the generator meant.
- **Mazes** (`mazes-screen`, `mz*` functions, all in `mazes.js` + `mazes.css`) — lazily loaded plug-in, under Maths: a number maze creator that is also playable on screen. A grid of numbers — **squares** (move up/down/left/right) or **hexagons** (pointy-top, odd rows shifted right, six neighbours) in three sizes — with exactly one route from START (top left) to END (bottom right). Seven patterns in `PATTERNS`, in two kinds. **Set rules** say which cells may be stood on, in any order: *multiples of X*, *factors of X*, *facts that make X* (cells show `a + b` / `a − b`), *odd numbers*, *prime numbers*. **Sequence rules** say what the next cell must hold: *count up by X*, *count down by X*. Tap cells to walk; tapping a walked cell steps back to it, and an illegal step is **refused** with a reason ("20 is not a multiple of 3 — 3 × 6 = 18") rather than drawn, which says nothing about the route because the dead ends are made of legal steps. **Show path** reveals the route; **Print PDF** writes the on-screen maze plus up to four fresh ones, one per page, followed by an answer key, through the same jsPDF engine and `pgHeader` as the Worksheets tab. Uniqueness, by kind: for set rules the passable cells form a **tree** — the route never touches itself except step to step, and every dead-end cell is placed touching exactly one passable cell — and a tree has one path between any two of its cells. For sequence rules steps are strictly monotonic, so routes are counted exactly by a forward/backward sweep, and any off-route cell lying on a complete route is reassigned a number with no legal step in or out (repairs only remove edges, so it terminates). Neither argument is trusted: `mzCount` walks every simple path using only `mzLegal`, the same predicate the player is held to, and a maze is kept only if the count is exactly one. Distractors are near misses (one or two off a multiple, odd composites like 51 and 91 for primes, facts that make X ± 1) rather than random numbers. `window.__MZ` is a debug handle used by the smoke test.
- **Turret** (`turret-screen`, `tr*` functions, all in `turret.js` + `turret.css`) — lazily loaded plug-in, under Maths: a three.js gun-turret shooter built to run on a budget Fire tablet. An NPC pilot flies; fighters swoop past; tapping near one **locks** it, fires a bolt, and slows time to a stop with the bolt hanging in mid-air while a flash-card question is asked; every visible fighter carries a target box with a callsign and range, and there is no fixed reticle — a shot goes where the finger lands. Right, and the bolt lands; wrong or out of time, and the fighter barrel-rolls away on a break checked to clear the bolt by `MISS_BY`. **A hit is decided, not detected**: a locked bolt is aimed at where the fighter's path puts it on arrival, so there is no collision test to get wrong. Answers by multiple choice (two buttons under each thumb; distractors are off-by-one, the neighbouring fact and the wrong operation), an on-screen keypad (fires on the right value, and misses on the first digit that cannot lead to it — for 35, a 4 or a leading 0 — so digits cannot be walked up), or speech through `spListen` (one claim per question; a **final** result naming another number is a miss, an interim one is not). A **sortie** is the complete deck for the set, shuffled, and ends when every fact has been answered right once; a miss comes back a few seconds later on a gold **ace** carrying that fact, and an ace that escapes unasked comes round again. Scored on first-try correct, sortie time and median right-answer time; bests per exact set at `nq.turret.best.<ops>_<max>[_tables]`, **from whole sorties only**. Per-fact records (`nq.turret.facts`: attempts, correct, last five results with time and mode) drive four levels — New, Learning, Shaky (a miss among the last three), Fluent (last three right with median under a per-mode threshold). It **never writes `ttFact_*`**. A **grown-up panel** behind a three-second hold on the gear plus a two-digit multiplication has Progress (per-op grids coloured by level, slowest and most-missed facts, recent sorties), Questions (ops, range, per-number filters — a fact is kept when either number of its family is picked — and a lock that hides the child's picker), Answers (mode, whether the child may switch, timer, fluency thresholds, sound) and Reset (scores, tracking, everything; two taps each; turret keys only). Around the questions: asteroids drift past all the time and thicken into belts, and any rock can be tapped to shoot it — no lock, no question — when a big one splits into pieces and a small one bursts; a few rocks are aimed at the ship, and fighters on strafing runs fire at it. A hit on the ship is a red edge flash and a jolt, nothing more. Fighters are Kenney Space Kit models (CC0, in `models/`, in the kit's own colours with the accent panels painted — red by default, gold on an ace — and squashed a little in height) fetched once, with a built-in dart until they arrive; they enter from off-screen on paths planned at spawn and bank like aircraft. The two guns are 3D hexagonal barrels outside the glass that turn to each shot and recoil. Bolts, engine glows, the sun and explosion shapes are crisp circles with an outline and a halo. Explosions are a few such circles and rings, in eight styles; the default adds a thin blue shockwave ring, which a shot rock gets too, and with "bitten circles" on (the default) every disc is eaten from just off its middle by a faster circle, so it is briefly a crescent. Fighters' back-facing rear panels are thrusters, glowing in their own colour — real lights on High. On Medium and High the fighters are shiny (Phong, darker panels shinier); on Low they are matte, so auto-quality drops the shine on a slow device. Quality also sets how finely the rocks — fractal, cratered lumps — are drawn. The stage fills the screen under the tab bar at any shape. A mouse over the stage steers the idle guns; on High a muzzle light lights the barrels and anything near for a moment after each shot. A lock no longer swings the turret, and the question with its answers — choices or keypad — sits in the middle of the screen. A rock that hits the ship breaks, without an explosion. Window grime (`textures/window-grime.png`, white with alpha, "Image by KamranAydinov on Magnific", credited on the briefing card) sits on the glass between the scene and the frame, cut out of the middle by a blurred copy of the window shape, and shows only as the turret faces the sun; a hit flashes red in the same stencil while the grime crossfades to red. A debug overlay (the "dbg" button), in collapsible categories, sets the lock distance (how far outside a fighter's target box a shot may land and still lock it) and both bolt speeds, picks the explosion style, toggles and tints the grime with a two-thumb strength range and the stencil's reach and fade (as a share of the screen's short side), sets each fighter's accent colour, squish, shine and thrusters (on/off and colour), toggles bitten circles, sets the hit colour, picks a version of each sound, shows the frame-time readout, and spawns swoops, strafing runs, incoming rocks, a belt or a hit flash on demand; its choices live at `nq.turret.debug`. Budget rules are in the file header: pixel ratio 1 plus a render scale per tier, an SVG cockpit, one directional sun with Lambert (per-vertex) lighting on flat-faceted meshes, bolts and glows as size-clamped points, fixed pools and no per-frame allocation, the ship fixed at the origin with the world turning round it, two clocks (world time scaled for bullet time, real time for aim and answers), the loop stopped with the screen, and a lost WebGL context rebuilt from scratch. Sound is synthesised with WebAudio, made on the Launch tap. `window.__TR` is a debug handle (`step()` drives the simulation by hand, since a background pane gets no rAF).
- **Sounds** (`sounds-screen`, `vs*` functions, all in `sounds.js` + `sounds.css`) — lazily loaded plug-in, a sandbox over the on-device vowel analyser in `audio.js`. A square plot of the vowel space shows all eight vowels where they sit for the current speaker, the three calibration corners ringed, and a live red dot with a fading trail for whatever the microphone is hearing; readouts give F1, F2, pitch, level and the nearest vowel with its confidence. Three controls: start/stop listening, **Calibrate** (the same three-noise warm-up the Learn runner uses — eee, ahh, ooo — with a hold meter), and a **smoothing** slider. `audio.js` could already hear a vowel but could not show you; this is the picture. Notes worth keeping: calibration writes the same `voice.v1` record (and `window.irVoiceAnchors`) the Learn runner reads, so recalibrating here fixes vowel items everywhere — and a **degenerate calibration is discarded rather than saved**, because three noises that are not three different noises leave a space in which every later reading is meaningless. Smoothing is a plain exponential moving average whose coefficient is the slider **squared** (`vsAlpha`), since the useful range is all at the smooth end. A frame that is silent, unvoiced or missing a formant **does not move the dot** — its formant estimate is not a quiet reading but a meaningless one, and letting it in sends the dot to a corner on every breath. The plot uses one scale for both axes so the distances you see are the distances the classifier works in. The render loop checks whether its own screen is still active and shuts the microphone down if not, since a plug-in has no hook into `onTabLeave`. `window.__VS` is a debug handle used by the smoke test.
- **Geometric Proofs** (`geo-proofs-screen`, `gp*` functions, all in `geometry-proofs.js` + `geometry-proofs.css`) — step-by-step proof builder in the style of **Oliver Byrne's 1847 Euclid**: flat vermilion/ultramarine/gamboge/black shapes on cream paper, and proof statements written with **inline coloured glyphs instead of letter labels** (`gpGlyphs` expands tokens like `[red-line]`, `[blue-circle]`, `[yellow-angle]`). **All 48 propositions of Book I** plus III.31 (Thales) in `PROPS` — the original nine (I.1, I.5, I.9, I.10, I.11, I.15, I.32, I.47, III.31) use raw coordinates; the other 39 live in `MORE_PROPS` and use the **named-point format**: `P: {A:[x,y],…}` with shapes referencing names (`{t:'line',p:'A',q:'B'}`, `{t:'circle',at:'A',thru:'B'}`, `{t:'poly',ptsN:[…]}`, `{t:'wedge',at:'B',from:'A',to:'C'}`). `gpResolve` computes wedge angles (always the non-reflex side) and radii, so no hand-entered trigonometry — prefer this format for any new proposition. I.47 uses the full Euclid argument (nine steps: I.46 squares, the I.14 collinearity that later serves as the I.41 rail, the I.31 parallel split, the two auxiliary triangles, right-plus-common angle addition, I.4, and I.41 doubling on each side) — its diagram's G–C–B collinearity and equal pivot wedges are exact in the coordinates, so do not simplify it back. Menu order is enforced by `gpOrd` sort (Book I numeric, then Book III). `window.__GP = {PROPS, SB_INSTRUMENTS}` is a debug handle used by validation scripts. Each step the user picks the correct next construction/justification from three shuffled choices; a correct pick reveals the SVG shapes tagged with that step (`data-gp-step`; strokes draw themselves in via `getTotalLength`, fills fade), appends a Byrne-style line to the proof ledger (Roman-numeral markers), and optionally pulses related shapes (`flash`). Wrong picks disable the choice and show a *why-not* explanation. Ends with a Q.E.D. panel; completion stored as `gpDone_<propId>`. Same self-contained plug-in pattern as `language-arts.js` (injects its own stylesheet/tab/screen, registers in `TAB_ENTRY`/`SCREEN_TAB`). Diagram convention: shapes with `z:0` are solid fills beneath the linework; wedge angles are in SVG screen coordinates (y down, clockwise from +x). A **Sandbox** sub-mode (`sb*` functions, toggle via `gpSetMode`) gives free-form straightedge + compass drawing with **key-point snapping**: points are the atoms (`sbState.pts`, each `{id,x,y,kind}`), segments reference two point ids and circles a centre id + radius, and every commit (`sbCommitObj`) registers new intersections (line×line, line×circle, circle×circle) as key points. Segment ends and circle centres snap to key points; a dragged circle's rim *sticks* when its radius passes within `SB_RIM` of a key point's distance (the Euclidean collapsing compass); dragging a segment out of an existing endpoint snaps to the collinear extension (`sbDirSnap` — Euclid's "produce the line"). Four Byrne ink swatches, snapshot-stack undo, and a "Begin with" seed select (`SB_SEEDS`: line / crossing lines / triangle / right triangle / blank). **Build-this-proof challenges** (`sbChal*` / `sbStartBuild`): eleven propositions carry a `build` block (I.1, I.2, I.3, I.9, I.10, I.11, I.12, I.16, I.22, I.32, I.46) — a seed plus ordered `targets`, each an expected circle (centre + radius) or segment (both endpoints; `any:` for symmetric alternatives; **`{from:[x,y], dir:[dx,dy], minLen}` for "produce the line" steps** where only one end and the direction are determinate) with ±3-unit tolerance, plus a glyph `instr` and a `miss` nudge. Seeds may be a plain segment array or `{segs, pts}` (bare points, e.g. I.2/I.12's floating point). A `needs: ['carry',…]` list renders an "Instruments called for" line in the challenge bar (advisory, not blocking — locked ones name the earning proposition). I.2 and I.12 are buildable with the base kit alone; I.3/I.22 need carry, I.16 needs midpoints, I.32 parallels, I.46 perpendiculars — the toolkit bootstraps itself, and I.2's own build is what unlocks carry. Because snapping makes correct constructions land exactly, targets are plain precomputed coordinates. A committed object matching any unfinished target is accepted and re-inked to the target's canonical colour; a mismatch is auto-undone with the current step's `miss` text. Progress is recomputed from canvas contents (`sbChalRecalc`), so user Undo just works; Clear restarts the challenge. Completion stores `gpBuilt_<propId>` ("△ built" seal on the menu card, beside "∎ proved") and offers "Now prove it" into the guided proof. Menu cards are `<div>`s with `data-act` Prove/Build buttons. **Progressive instruments** (`SB_INSTRUMENTS` / `sbHas` / `sbInstrumentsRender`): completing a proposition (proved *or* built) permanently unlocks its construction as a one-stroke snap power in the sandbox, shown as chips above the board — always-on collinear extension (Postulate 2); **carry lengths** (I.2/I.3: the rim also sticks at any drawn segment's length — the non-collapsing compass; the source segment pulses as the cue); **bisect angles** (I.9: segment from a vertex snaps to the bisector of any two rays there); **midpoints** (I.10: every segment shows a hollow-dot virtual midpoint, snappable by ends/centres/rims and materialised into a real point on commit via `sbVirtualPts`); **perpendiculars** (I.11/I.12: segment from any point *on* a line snaps square to it); **parallels** (I.31: segments snap parallel to any existing segment). All direction candidates funnel through `sbDirSnap` (smallest angular offset wins; key-point snap always beats direction snap); unlock checks read localStorage live, and chips refresh on `gpFinish`, build completion, and sandbox entry.

### Money: sizing and assets

Every denomination carries `mm`, its real-world width. CSS sizes each piece as `mm * --mn-ppm`, so **all pieces are to scale against each other** — a dime really is smaller than a penny, an AUD $2 smaller than an AUD $1, and a note ~6.4x a quarter.

A pile renders as **one group per distinct denomination** (`.mn-stage` > `.mn-col`), highest value first. `mnFitStage()` tries **both orientations** and keeps whichever makes the pieces bigger: `mn-cols` stacks each denomination vertically (columns side by side), `mn-rows` lays each horizontally (rows stacked top-to-bottom). Wide bills win big in one orientation, so this is what makes them fill the space — don't drop it back to a single fixed orientation. For each orientation it binary-searches `--mn-ppm` (via `mnMaxPpm`) up to the largest value that fits `MN_WIDTH_FILL` (0.98) of the box width and all its height. A group draws at most `MN_COL_MAX` (12) real pieces; beyond that a `×N` badge shows the true count (so "all pennies" is a neat labelled stack, not 137 coins). Because a wide pile can inflate the box's own measured width, `mnFitStage` first collapses `--mn-ppm` to the minimum, reads the true box width, then grows into that fixed reference. `.mn-container` is 880px wide to give bills room. The Build toolbar is a wrap-row, not columns, so it uses `mnFitHeight` (height-only).

USD pieces are real **photos hot-linked from Wikimedia Commons** (`d.img`, all public domain — 4 individual coin obverses + 5 individual note obverses; **not** stored in the repo). `mnPieceHTML` layers the `<img>` over the drawn SVG (`mnCoinSVG`/`mnBillSVG`) inside a `.mn-photo` wrapper, so a slow fetch shows the drawing until the photo arrives and a failed fetch (`onerror` removes the img) leaves the drawing in place — which is why USD denoms keep their `face`/`edge`/`ink` colours even though they normally show a photo. `.mn-photo` is `overflow:hidden` so the wrapper's `border-radius` (50% for coins, 3px for notes) clips the photo; sources are tight-cropped so `object-fit:cover` needs no per-image tuning. Non-USD currencies render as drawn SVG only.

The bills are **individual** note images, not the old `USDnotes.png` composite — you can't hot-link one note out of a 7-note composite (and it's 8.9 MB). To swap or add USD art, resolve a Commons thumbnail URL (keep it public-domain) and drop it in `d.img`; nothing to commit.

The nickel uses `File:2026-nickel-transparent-512.png` — a background-removed version (outer white flood-filled to transparent, interior highlights kept) uploaded to Commons, because the stock Jefferson-nickel scan is opaque-white and left a ring under the circular crop. The other three coins are naturally transparent on Commons.

### Money: rules to preserve

- **Denomination values are always minor units** (`v: 25` is 25¢, `v: 2000` is a $20 bill) — never store floats, money math is integer-only
- `mnFewest` uses **DP, not greedy** — greedy is wrong for non-canonical denomination sets, so keep it if new currencies are added
- `mnRandomAmount` steps by the **smallest denomination**, so the target stays makeable in currencies with no 1¢ — do not switch to a plain random integer
- Not every amount is makeable: CAD/AUD have no 1¢, so `mnChangeOptions` can return empty (e.g. $1.37 CAD) — that path must stay handled
- `MN_COL_MAX` caps pieces drawn per column; higher counts get a `×N` badge so "All 1¢" of a large amount stays responsive
- Amount fields are **cash-register entry** (`mnAttachAmount`): digits fill from the right (1234 → 12.34), so there is never an ambiguous bare integer and no placeholder is needed. Read them with `mnFieldCents`, not `parseFloat`
- The mode panels (`#mn-identify` etc.) must stay `width: 100%` — the container centres its children, so without it the pile box shrinks to content and the 90%-width sizing has nothing to work against

`.tt-btn-group` (shared by Fractions, Times Tables, and Money mode toggles) has `flex-wrap: wrap`, and `.tt-container`/`.fr-container` trim their side padding under 420px — both needed so those tabs don't overflow a phone viewport.

### Money: Shopping mode

A **fixed catalogue** (`MN_SHOP_CATALOG`), not a live storefront. A static page cannot query a retailer: cross-origin requests are blocked, and Amazon's Product Advertising API needs server-side credential signing that would leak in a public page. So prices live in the catalogue and only the **photos** are fetched, hot-linked from Wikimedia Commons; the search term filters the catalogue. Photos are CC-licensed, so each item carries `by`/`lic` and renders a credit in its tile `title` — keep that if you edit the catalogue. The grid is built on first entry to the mode (not in `mnInit`) so visitors who never open Shopping don't fetch ~10 external images; `MN_IMG_FALLBACK` hides a tile's image if a hot-linked URL ever rots.
